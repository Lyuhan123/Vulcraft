# 2026-08-29

## Vulkan mod (Cleanroom 1.12.2) 性能优化

对 `com.yuhan123.vulkanmod` 做了 6 项优化（10 个文件，全部编译通过）。

### 已改动
1. **帧同步重构（最大收益）**
   - `Renderer.endFrame()` 原先在 `submitFrame()` 前调用 `waitFences()`，导致每帧 CPU/GPU 完全串行。
   - `VulkanImage.uploadSubTextureAsync()` 原先每次 `glTexSubImage2D` 都 `submit` + `vkWaitForFences`，光贴图/动画纹理/字体/皮肤每帧都会触发几十次全流水线排空。
   - 现改为：上传命令批处理进 `ImageUploadHelper`（已有设施，`SpriteUpdateUtil` 就在用），`endFrame()` 只提交不等待；staging buffer 的 `reset()` 推迟到下一轮同槽位 `beginFrame()`（此时 `inFlightFences` 已保证上传完成）。
   - `Synchronization` 新增非阻塞 `reapSignaled()`，轮询 `vkGetFenceStatus` 回收已完成的上传 command buffer。
   - `Renderer.beginFrame()` 里用 `ImageUploadHelper.hasPendingCommands()` 做保护，避免帧外未提交的上传被 reset 清掉。

2. `GraphicsPipeline.createGraphicsPipeline()` 删除残留的 `System.out.println`（每次 pipeline 缓存未命中都同步写 stdout）。
3. `PipelineState.hashCode()` 改为构造时预计算缓存（原来用 `Objects.hash`，每次绘制分配 `Object[6]` + 5 个装箱）。
4. `Pipeline.DescriptorSets.updateDescriptorSet()` 去掉每次的 `VkDescriptorBufferInfo.Buffer[]` / `VkDescriptorImageInfo.Buffer[]` 堆数组；顺带修了 `createDescriptorSets()` 里 `sets` LongBuffer 的原生内存泄漏。
5. `GlStateManagerMixin`：glBegin/glEnd 顶点捕获改为扁平 `float[]` + 复用 ByteBuffer（原来每顶点 `new float[5]`、每次 glEnd `memAlloc/memFree`）；`buildFormatFromPointers()` 按指针状态缓存 VertexFormat。
6. `Drawer.draw()` 传给 `AutoIndexBuffer.checkCapacity()` 的量纲错误（传 indexCount，方法按 vertexCount 比）已修，扩容改为 `max(2x, 需求)`。

### 关键架构事实（后续改动必读）
- 帧生命周期挂在 `MinecraftMixin`：`beginFrame` = `runGameLoop` HEAD，`endFrame` = `runGameLoop` RETURN。整个 `runTick` 都在帧窗口内，所以纹理动画上传一定在 beginFrame/endFrame 之间。
- `framesNum = 3`；`stagingBuffers[frame]` 每帧槽一个，各 64MB；`currentFrame` 只在 `submitFrame()` 末尾递增。
- 上传批处理与主帧提交**都在 graphics queue**，且上传先提交 → 同队列顺序保证拷贝先于绘制执行；这是 staging buffer 延迟 reset 的正确性依据。
- `waitFences()`（阻塞全刷）现在只被 `preInitFrame`（递归 runTick）和 `recreateSwapChain` 调用，不要加回每帧路径。

### 待确认的既有问题（未改，属功能非性能）
- `PipelineManager.shaderMap` 是 `HashMap<VertexFormat, ShaderInstance>`，`glDrawArrays` 用 `buildFormatFromPointers()` 重建的 VertexFormat 去查。若 1.12.2 的 `VertexFormat` 没有 `equals/hashCode`（走 identity），则除 `POSITION_TEX_COLOR_NORMAL` 常量分支外都会查不到 shader 而静默丢弃绘制。我的缓存改动对该行为是中性的（改动前后结果一致），但值得单独确认。

## Session 2 — 第二轮优化（矩阵路径 / 显示列表 / 持久 VBO）

在上一次“帧同步”优化之后继续，针对 CPU 侧热点。全部 `./gradlew build --offline` 通过。

### 改动
1. **矩阵路径（最大收益）** — `MatrixState.apply()` 每次 `translate/rotate/scale/loadIdentity/popMatrix` 都会调 `VRenderSystem.calculateMVP()`，后者 `new Matrix4f` ×2 + `asFloatBuffer()` ×4（每次调用都新建 FloatBuffer 对象）+ 一次 4×4 乘。1.12.2 每帧几万次这类调用 → 每秒数百万短命对象。
   - `VRenderSystem` 增加 `MODEL_VIEW_FB / PROJECTION_FB / TEXTURE_FB / MVP_FB` 缓存 FloatBuffer 视图 + `MV_SCRATCH / P_SCRATCH` 复用矩阵；`calculateMVP()` 零分配。
   - MVP 改为**惰性**：`apply()` 只置 `mvpDirty`，`ShaderInstance.apply()` 开头 `flushMVP()` 每帧每绘制算一次而不是每次矩阵操作算一次。
   - `getMVP()` 也会 flush，保证任何读取路径都拿到最新值。
   - `MatrixState` 增加 `matrixPool`（上限 256）复用 `pushMatrix/multMatrix` 的 Matrix4f；`popMatrix` 归还。

2. **显示列表重放** — `DisplayListManager.replayDraw()` 每次重放绘制都要 `new Matrix4f` ×4 + 一次矩阵求逆 + `new float[16]` 保存/恢复。
   - 捕获期就把 `startMV^-1 * capturedMV` 折叠成单个 `relative` 矩阵（`startMV` 对整个 list 恒定），重放只剩 `P * (currentMV * relative)`。
   - 复用静态 scratch 矩阵 + 缓存 FloatBuffer，零分配、零求逆。
   - 借惰性 MVP 去掉 save/restore：写入后 `markMvpClean()`，finally 里 `markMvpDirty()`。

3. **持久 VBO（第二大头）** — `GlStateManagerMixin.glDrawArrays` 原来每次都把 VBO 区间 `memcpy` 进每帧顶点缓冲；区块段内容只在重建时变，等于每帧白拷几十 MB。
   - `VkGlBuffer` 增加 `vertexBuffer`（`MemoryTypes.HOST_MEM` 常驻镜像），`glBufferData` 时上传一次；`glDrawArrays` 用 `Drawer.drawPersistent(vb, byteOffset, ...)` 直接带偏移绑定，本帧零拷贝。
   - 重新上传时**新建**缓冲，旧的 `scheduleFree()`：在飞帧继续读旧缓冲，`MemoryManager` 延迟 3 帧销毁是安全的——同队列提交顺序保证「帧 F 的 fence 等到 → F 之前所有帧（即所有读者）都已完成」。
   - 不要用 `GPU_MEM`：transfer queue 可能与 graphics 不同族，跨队列需要信号量，改用 HOST_MEM 规避。
   - `glDeleteBuffers` 同步 `freePersistent()`；分配失败 catch 后回落到原来的拷贝路径。

4. `GraphicsPipeline.getHandle()`：`computeIfAbsent(state, this::createGraphicsPipeline)` → 显式 `getLong/put`，去掉每次绘制的绑定方法引用对象分配。

5. **管线缓存落盘** — `Pipeline` 的 `VkPipelineCache` 原先从不保存，每次重启都重编译所有管线（首帧/新状态组合卡顿）。新增 `vulkanmod_pipeline_cache.bin`（工作目录），格式 = `[16B pipelineCacheUUID][原始 blob]`，按 UUID 校验驱动匹配。

6. 修两个泄漏：`MemoryManager.Map()` 每次泄漏一个 `memAllocPointer`（→ 改为 `mapPointer()` 用 MemoryStack）；`VulkanImage.doFree()` 把 `mainImageView` 销毁 N+1 次而每个 level view 都泄漏。

7. `VTextureSelector.bindShaderTextures()`：missing texture 解析改成单条缓存（原来每次绘制都查 map + `getGlTextureId()`）。

### 关键事实 / 易踩坑
- **JOML 语义（实测 JOML 1.10.9，见 `/tmp/jomltest/T2.java`）**：`Matrix4f.get(FloatBuffer)` 从 `position()` 写入 16 个 float 且**不推进 position**；`Matrix4f.set(FloatBuffer)` 从 `position()` 读，**要求 remaining ≥ 16**（position=3 时直接 IndexOutOfBounds）。所以缓存的 FloatBuffer 每次用前必须 `clear()`。
- LWJGL 的 `size_t*` 映射为 `PointerBuffer`（不是 `LongBuffer`），`uint8_t[16]` 映射为 `ByteBuffer`（不是 `IntBuffer`）。`vkGetPipelineCacheData` 签名即 `(VkDevice, long, PointerBuffer, ByteBuffer)`。
- 本项目 `src/main/java/org/lwjgl/**` 有一份**内联的 LWJGL 源码副本**（PointerBuffer / MemoryUtil / MemoryStack 等），会遮蔽 jar 里的同名类，写新代码时类型容易对不上。
- `glBufferSubData` 全项目没有实现/覆写，`glBufferData` 是唯一的 VBO 变更入口（GL15 / ARB / OpenGlHelper 三个 mixin 都转发到 `VkGlBuffer.glBufferData`）——这是持久 VBO 保持同步的前提。
- `VkGlBuffer.glBufferData(target=GL_ARRAY_BUFFER, long size, usage)` 会抛 `IllegalStateException`（switch 只处理 PACK/UNPACK），既有行为，未改。
- 编译用 `./gradlew build --offline`（Zulu 25 toolchain），约 40s，产物 `build/libs/vulkanmod-1.0.0.jar`。

## Session 3 — runClient 实机验证

用 `./gradlew runClient --offline` 跑了两轮实机验证（`run/client` 里有现成的 `New World` 存档，启动后会自动进世界，因此区块/实体/显示列表路径都能覆盖到）。

### 结果
- 第二轮（含全部修复）**零** `Client thread/ERROR|FATAL`；唯一异常是开发环境固有的 `java.io.IOException: Mixin config does not reside in a jar file`。
- `[DLDBG]` / `[RPYDBG]` 都有输出 → 显示列表捕获与重放路径（我改过的 relative 矩阵）实际跑通。
- 世界里出现 `vkCmdDrawIndexed(): ... VK_DYNAMIC_STATE_LINE_WIDTH` 等 VUID，与基线**完全一致**，说明绘制路径没变。
- 残留的 VUID 全是既有问题，与本次改动无关：
  1. `vkCmdPipelineBarrier(): Barriers cannot be set during subpass 0 ... with no self-dependency` —— `VulkanImage.readOnlyLayout()` 在 render pass 内被 `DescriptorSets.needsUpdate()/updateDescriptorSet()` 调用。render pass（`RenderPass.createRenderPass()`）只声明了 EXTERNAL↔0 的依赖，没有 self-dependency。可选修法：给 subpass 加 self-dependency，或把 TRANSFER_DST→SHADER_READ_ONLY 的转换挪到上传批次末尾（`ImageUploadHelper.submitCommands()` 时统一转），后者更干净且能省掉绘制中的 barrier。
  2. `vkCreateGraphicsPipelines(): ... Output value declared at Location 2 ... no corresponding Input` —— 顶点着色器输出了片元没消费的 UV2 varying，harmless。
  3. 退出时 `vkDestroyDevice(): ... 3064 leaked objects`（都是 `VkImage[GlTexture N]`）——既有泄漏。

### 自己引入并修掉的一个 bug（值得记住）
`Pipeline.PIPELINE_CACHE_FILE` 原本声明在 `PIPELINE_CACHE = createPipelineCache()` **之后**。静态初始化按文本顺序执行，导致 `createPipelineCache()` 里读到的是 null → NPE（被 `loadPipelineCacheData` 的 catch 吞掉，表现为缓存永远加载不了、只在日志里打一行栈）。已把常量移到 `PIPELINE_CACHE` 之前，并加了兜底：带 initialData 创建失败时删文件并用空缓存重试，避免坏缓存文件导致启动崩溃。

### 环境坑
- `taskkill` **不带 /F 杀不掉** java.exe（console 子系统，"can only be terminated forcefully"），所以拿不到干净退出 → `Vulkan.cleanUp()` 不执行 → **pipeline cache 的落盘路径没能实测**（保存逻辑本身在 `destroyPipelineCache()`，正常退出时会走 `shutdownMinecraftApplet` 注入）。加载路径已按 UUID 校验 + 失败兜底。
- 停掉 gradle 的 `runClient` **不会**杀掉游戏 JVM，会留下孤儿进程；下次构建可能撞 `.gradle/*/fileHashes.lock`（Access is denied）。解法：`./gradlew --stop`，然后手动 `taskkill /F` 掉残留 java。
- 本环境 PowerShell 工具**没有输出回显**（`Get-Process` 等一律空），wmic 被安全策略禁用；要用 `tasklist | grep -i java` 配合 `awk '{print $2}'` 取 PID。

## Session 4 — 第三轮优化（barrier / line width / 显示列表持久几何）

`./gradlew runClient --offline` 实机验证通过，世界内跑起来后 VUID 对比（基线 → 现在）：

| VUID | 基线 | 现在 |
|---|---|---|
| `vkCmdPipelineBarrier(): Barriers cannot be set during subpass 0` | 10（撞 duplicate_message_limit，实际更多） | **1**（仅启动期一次，绘制中已为 0） |
| `vkCmdDrawIndexed(): ... VK_DYNAMIC_STATE_LINE_WIDTH` | 10（同上） | **0** |
| `vkCreateGraphicsPipelines(): SPIR-V Interface ... Location 2` | 2 | 4 |

第三项只是 informational（"This is not invalid"，顶点着色器输出了片元不消费的 UV2 varying），无害。Client thread 的 ERROR/FATAL 始终为 0。

### 改动
1. **把纹理布局转换挪出 render pass** —— `VulkanImage.readOnlyLayout()` 在 `DescriptorSets.needsUpdate()/updateDescriptorSet()` 里被逐绘制调用，render pass 没有 self-dependency，于是每次都发非法 barrier。
   - `ImageUploadHelper` 增加 `pendingReadOnly`（`ObjectOpenHashSet<VulkanImage>`，identity 语义）；`submitCommands()` 时先 `flushPendingTransitions()`，在同一个上传 command buffer 末尾统一转 SHADER_READ_ONLY，再 submit。
   - `VulkanImage.readOnlyLayout()` 增加 `isPendingReadOnly(this)` 早退，避免"已排队但批次还没提交"这段窗口里仍然在 pass 内发 barrier。
   - `uploadSubTextureAsync()` 结尾 `addPendingReadOnly(this)`；`createTextureImage()` 里对**纯采样**图像（usage 有 SAMPLED 且无 COLOR/DEPTH_ATTACHMENT 位）也登记一次，覆盖"建了但从没上传"的纹理。附件类图像刻意不登记（否则会和 render pass 自己的转换打架）。
   - 正确性依据：上传批次与帧 command buffer **同队列且上传先提交**，队列内提交顺序即执行顺序；descriptor 里写死的 `imageLayout` 本来就是 `SHADER_READ_ONLY_OPTIMAL`（见 `ImageDescriptor` 构造），现在才真正对得上。

2. **LINE_WIDTH 一律动态** —— `GraphicsPipeline.createGraphicsPipeline()` 原来只在 topology==LINE_LIST / polygonMode==LINE 时才把 `VK_DYNAMIC_STATE_LINE_WIDTH` 放进 dynamicStates，而 `Renderer.resetDynamicState()` 每帧无条件 `vkCmdSetLineWidth`，于是每绘制报 VUID。改成始终加入；`resetDynamicState()` 开头已经设了合法默认值 1.0，安全。

3. **显示列表几何持久化** —— 原来每次 `glCallList` 重放都要把每段冻结顶点数据 `memcpy` 进每帧顶点缓冲；实体模型是静态的，等于每帧白拷。
   - 编译期（`glNewList`..`glEndList`）用可增长的 `ByteBuilder` 把该 list 所有 draw 的顶点**首尾相接**收集起来；`endList()` 时一次性 `new VertexBuffer(length, HOST_MEM)` 上传（每个 list 一次分配，而不是每段一次）。
   - `CapturedDraw` 记 `byteOffset`，重放走 `Drawer.drawPersistent(vb, byteOffset, ...)`，本帧零拷贝。
   - 保留 fallback：上传失败时退回逐段 CPU 镜像 + `Drawer.draw()`。
   - `startList` 覆盖旧 list、`deleteLists` 都会 `free()`（持久 buffer `scheduleFree()`，CPU 镜像 `memFree`）。
   - 注意：`slice(pos, size)` 用的是"相对 src 当前 position 之后 size 字节"，靠 `data.remaining() >= size` 做边界保护；`ByteBuilder.buffer()` 必须 `clear()` 后再交给 `copyBuffer`（后者用 `memAddress(src)`，认 position）。这套打包逻辑我单独写了个 standalone 测试验过（/tmp/dltest/T.java）：offset 0/16/32、字节全对、源 position 不被破坏。

### 下一轮可考虑（未做，需 profile 支撑）
- **UBO 动态偏移的浪费**：block shader 有 2 个 UBO（顶点 MVP 64B，片元常量 ColorModulator/FogColor/FogStart/FogEnd 共 40B）。两个都走 `UNIFORM_BUFFER_DYNAMIC`，NVIDIA 上 minUniformBufferOffsetAlignment=256 → 每绘制吃掉 **512 字节** stride，其中片元那 40B 其实是**每帧常量**。把片元 UBO 改成静态绑定（每帧写一次），stride 能降到 256。5000 draw/帧的话约省 1.2MB/帧的 UBO 增长。要动 descriptor layout，风险中等。
- 退出时 `vkDestroyDevice(): 3064 leaked objects (VkImage[GlTexture N])`：确认**不是运行时泄漏**——`allocateImage()` 会 `free()` 旧图，`glDeleteTextures` 也走 `addToFreeable`；那 3064 只是硬杀进程时仍存活的纹理（`MemoryManager.freeAllBuffers()` 只清 pending 列表，不销毁活对象）。无需处理。

### 环境补充
- 启动后**约 3~4 分钟**才会加载完资源进世界（日志会长时间无输出，看着像卡死其实没有）。判断进度看 `[VKDBG]`（绘制）/ `[DLDBG]`（显示列表编译，模型烘焙后才出现）/ `Loading dimension`。
- 停 `runClient` 后务必手动清 java 进程，否则残留实例会占着存档、并让下次构建撞 `fileHashes.lock`。清法：`for p in $(tasklist | grep -i '^java.exe' | awk '{print $2}'); do taskkill /F /pid $p; done`。撞锁则 `./gradlew --stop`。

## Session 5 — FPS 实测与关键修复（validation layers）

### 结论先行：FPS 34 → ~139（约 4 倍），根因是 validation layers 没关

加了 `FrameProfiler`（`render/util/FrameProfiler.java`，每 120 帧打一行 `[VKPROF]`：fps / frame / cpu / fenceWait / submit / apply / draw / draws / binds / descUpd / vbCopy / ubo），用日志实测定位：

| 指标 | validation ON | validation OFF |
|---|---|---|
| fps | ~34 | **~139**（min 104 / max 210） |
| frame | 29.4ms | 7.1ms |
| apply（shader apply 合计） | 7.4ms | 1.9ms |
| draw（命令录制合计） | **16.7ms** | **1.6ms** |
| fenceWait | 0.03ms | 0.01ms |

- **永远 CPU-bound**（fenceWait≈0.01ms，GPU 全程空闲），FPS 完全取决于录制/CPU 侧。
- 大头是 `vkCmd*` 逐调用过 validation layer（~7µs/调用）；`Vulkan.ENABLE_VALIDATION_LAYERS` 原来是写死的 `true`。
- 修复：改为 `Boolean.getBoolean("vulkanmod.validationLayers")`，默认 false；需要调试时 `-Dvulkanmod.validationLayers=true`。这是本次最大的单点收益。
- 剩余 frame≈7ms 里：apply 1.9 + draw 1.6 + 约 3.5ms 是 vanilla 逻辑（tick/实体/区块重建/GUI），不属于渲染器，难再大幅压缩。
- `FrameProfiler` 留在代码里（每次绘制 3 次 nanoTime，开销可忽略），是后续调优的测量工具；`ENABLED` 可关。

### 环境修复（绕开 Unimined 的 javaagent 问题）
- **Unimined 注入的 `-javaagent:juuxel/unprotect-1.3.0.jar` 崩了**（`NoClassDefFoundError: org/objectweb/asm/ClassVisitor` → 补 asm → `asm.tree.ClassNode` → 补 asm-tree → `org.apache.logging.log4j.LogManager` → 补 log4j-api）。这个 agent 的 manifest 只声明了 `Premain-Class`，依赖全靠系统 classpath 提供，而 Unimined 现在没把它带上。
- 处理：把 `asm-9.10.1 + asm-tree-9.10.1 + log4j-api-2.19.0` 打进 agent 做成 fat jar，覆盖了 gradle 缓存里的 `unprotect-1.3.0.jar`。原件备份在 `/tmp/agent/unprotect-1.3.0.orig.jar`。**注意：如果清缓存/重解析会还原，届时需重新打 fat jar。**
- 顺带：`gradle.properties` 里有个未提交的 `extra_jvm_args = -XX:StartFlightRecording=...`（注释写着 TEMPORARY）会把 JVM 参数塞进主类位置导致 "Could not find or load main class"，已 `git checkout` 还原为空。用户若想再开 JFR，建议用 `org.gradle.jvmargs` 或修好 Unimined 的 arg 拼接，别放 `extra_jvm_args`。
- 启动顺序经验：`taskkill /F` 清 java → `./gradlew build --offline` → `./gradlew runClient --offline`；进世界约 3~4 分钟，看 `[VKPROF]` 或 `joined the game` 判断进度。
